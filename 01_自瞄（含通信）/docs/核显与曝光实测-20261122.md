## 结论

- Intel Iris Xe 能运行当前 YOLOv5；切到核显后，本轮进程 CPU 平均约 160–189%，
  原桌面 CPU 实测约 305%。核显阶段平均封装温度约 82–85°C，但仍有 94–97°C 峰值，
  不能认定散热问题已解决。
- 缩短曝光确实提高相机交付速度；当前完整视觉循环未追平 98/122 FPS。
- 各阶段画面和目标负载有变化，以下数值是实际使用中的观测，不能直接当成严格 A/B
  的提升百分比。特别是 10/8 ms 阶段约 86%/95% 的帧有目标，15 ms 核显测量段无目标。
- 核显还需要更充分的识别一致性校验；本轮没有永久切换桌面默认配置。
- 已捕获一次明确的窗口关闭原因：16:38:08，OpenCV 返回 `q`（ASCII 113），
  程序正常退出，退出码 0，没有 SIGINT/SIGTERM/SIGSEGV/SIGABRT。
  这只能解释该次关闭，不能把历史退出全部归因于按键，也没有证明所有重开均为自动重启。

## 为什么 CPU 热

短时线程采样：主线程约 95%，三个较忙的工作线程各约 48%，全部线程合计约 302%。
同模型 CPU 编译属性为 LATENCY、4 个推理线程、1 个流、启用线程绑定，使用 FP32。
正常程序持续处理最新图像，推理之外还有预处理、后处理、图像转换和图形调试。
这些负载足以持续占用多个核心。温度/热节流数据证明散热余量有限；尚未检查风扇或
散热接触，不能把所有温度问题归因于单个代码点。
CPU 基线的检测阶段约 12.51 ms / 循环 16.87 ms，约占循环时间的 74%；
该阶段同时包含预处理、推理、后处理和检测绘图，不能把 12.51 ms 全部当作纯推理耗时。

代码中确认的可优化开销（尚未实施或量化各自收益）：

- `tasks/auto_aim/yolos/yolov5.cpp:88–96`：每帧分配 640×640 输入并创建 InferRequest。
- 同文件 `:207,243–261`：每帧复制整幅图像、绘制、缩放并显示检测窗口。
- `tests/auto_aim_test.cpp:429–462`：每帧构造控制面板并重复绘制部分区域。
- 同文件 `:493` 和 `tools/logger.cpp:26`：每帧 info 日志，且每条 info 刷新输出。
- 同文件 `:620–642`：每帧构造/序列化调试 JSON，包含未请求保存快照时的数据。
- 未显式限制 OpenCV 图像处理线程；本机 Python/OpenCV 同库默认报告 8 线程，
  可继续检查与 OpenVINO 线程池并存的开销。不能仅凭线程个数判定最佳配置。

USB 线程使用 poll 等待，接收/看门狗也有等待；没有发现其持续空转足以解释 300%
CPU 的证据。没有发现按 CPU 温度自动退出的应用逻辑。

这是相同输入的一致性检查，不是有真值的准确率评测；不能承诺两个后端识别完全一致。

OpenCL ICD。已下载 Ubuntu 22.04 仓库的 Intel OpenCL 22.14.22890 和依赖，解压到

没有安装系统软件包。实际识别为 Intel Iris Xe [0x9a49]，GPU 配置明确指定 GPU，
没有使用 AUTO 后端回退 CPU。这是临时驱动方案，依赖本轮构建目录保留。

虽然本轮所有完成的 GPU 测量均能推理并正常结束，仍需使用正式匹配的驱动复测长期稳定性。

## 优化顺序（本轮未实施）

1. 将核显驱动和运行环境整理为可复现方案，在固定录像与固定现场目标下核对识别和稳定性。
2. 复用 InferRequest 与输入缓冲，减少每帧分配和大图复制；这是保留模型与控制逻辑的优化候选。
3. 检测/控制继续逐帧运行，调试窗口降到约 10–15 Hz，普通日志降频，截图数据按需构造。
4. 分别测试 OpenVINO 1/2/4 线程及 OpenCV 线程组合，按持续帧率、延迟和温度选择，
   不预先承诺限制线程一定提速。当前安装的 OpenCV 不响应 `OPENCV_FOR_THREADS_NUM=1`，
   不能只设置该环境变量就声称已限线程。
5. 曝光先以 12 ms 作为候选，再比较 10 ms；8 ms 已让相机达到约 122 FPS，
   完整处理仍约 65 FPS，继续提高采集速度会增加转换负载并减少进光，当前优先级较低。

每项应在相同目标、画面和稳定散热条件下单独对照，保持 USB 在线，记录处理 FPS、
SDK→处理结束延迟、识别丢失、CPU 温度及热节流，不用单纯采集 FPS 代替实际处理 FPS。
