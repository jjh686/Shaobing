# 原生 Ubuntu 22.04 导航源码与通信测试包

快速操作入口：[快速部署与通信测试](快速部署与通信测试.md)。本文保留详细诊断和部署边界。

日期：2026-11-10。目标：沿用小电脑已有 ROS2 Humble、雷达 SDK 和驱动环境，迁移导航源码并验证 PC→USB云台→CAN底盘的通信。

## 包含内容

- `src/pb2025_sentry_nav`：展开后的导航源码，包括 PointLIO、重定位、地形分析、规划跟踪、实车启动与参数。
- `src/rm_chassis_comm`：PC C++ 通信、协议公共源码、坐标桥、启动配置与测试。包内的 C 协议源码参与 PC 构建，须保留。
- `scripts`：编译及失能通信测试入口。
- `SOURCE_MANIFEST.json`：源码来源与 SHA256；`SHA256SUMS`：包内文件校验。

未打包 SDK、ROS安装环境、WSL配置、完整云台/底盘烧录工程、Gazebo仿真工程、采集地图或历史编译结果。导航仓库自带的旧 `livox_ros_driver2` 整个目录已排除，沿用目标机器现有驱动，避免同名包冲突。仓库中少量仿真启动引用和点云转换源码仍保留，未修改上游依赖关系。

## 解压位置

将 ZIP 复制到小电脑，解压后保留 `rm_nav_source_20261110` 完整目录，例如 `~/rm_nav_source_20261110`。不要覆盖自瞄或已有驱动工作区。

以下命令均在小电脑的 Ubuntu 终端执行：

```bash
cd ~/rm_nav_source_20261110
sha256sum -c SHA256SUMS
```

## 第一步：只编译通信包

不需要加载雷达 SDK 或驱动。脚本不会安装依赖或修改系统设置。

```bash
bash scripts/build_comm.sh
```

若缺少 ROS 标准依赖，保留完整编译错误再处理；不要把 Windows、WSL 的 build/install 复制过来替代编译。

## 第二步：软件预览

第一个终端：

```bash
cd ~/rm_nav_source_20261110
bash scripts/comm_test.sh preview
```

第二个终端：

```bash
cd ~/rm_nav_source_20261110
bash scripts/watch_comm.sh
```

预期 `Preview: hardware not opened`、`enabled=false`、`route=2`。这个结果验证程序启动和 ROS 话题，不代表 USB/CAN 已接通。两个终端都可按 Ctrl+C 退出。

## 第三步：连接云台 USB 做失能收发测试

前提：电控已核对并接入本次协议；确认标准 CAN ID 0x320/0x321 无冲突。原来的 SP 云台固件只有自瞄数据，不会自动产生新版底盘/关节反馈。此包不包含烧录工程，也不执行刷写。

实体连接：小电脑→USB→云台板→CAN→底盘板。云台负责USB分流、CAN转发和关节采样；底盘负责指令接收、安全许可、轮速控制与反馈。测试时禁止底盘运动，保留实体急停。关闭自瞄的物理串口占用和其他串口工具；本测试不启用SP代理。

先退出软件预览，再查看实际设备：

```bash
ls -l /dev/serial/by-id/
```

将下面设备路径替换成实际值：

```bash
bash scripts/comm_test.sh usb /dev/serial/by-id/实际设备名
```

第二个终端运行 `bash scripts/watch_comm.sh`。本过程不发布运动速度、不调用使能；不要调用 `set_enabled=true`。源码的服务接口仍存在，试验期间不要由其他程序使能它。

| 观察项 | 含义 |
| --- | --- |
| `USB connected; STOP handshake only` | 串口已经打开；尚不能证明底盘回复 |
| `enabled=false` | 保持失能，试验中必须保持此值 |
| `received_bytes` 持续增加 | USB收到了字节；不等于新协议校验成功 |
| `decoded_feedback` 持续增加 | 收到通过分帧和CRC解码的底盘反馈；会话、序号及ACK是否被接受还须结合下项判断 |
| `feedback_age_ms` 为数值且持续刷新 | 收到本会话、已发送序号及ACK等检查通过的新反馈；默认300ms后会判过期 |
| `decoded_gimbal` 增加 | 收到可解码关节反馈；有效性还需检查 `gimbal_fresh`、标定状态 |
| `Ready, disabled` | 底盘READY与STOP确认等条件满足，当前仍失能 |
| `Waiting for actual chassis READY/STOP ACK` | 仍缺就绪条件或确认；默认固件许可关闭时可能出现，需看实际电控状态 |
| `fault_mask` | 故障位，定义见 `src/rm_chassis_comm/PROTOCOL.md` |

`decoded_feedback` 只是解码计数；结合持续新鲜的 `feedback_age_ms` 才能确认反馈被本次会话接受。通信通过后仍需验证电机方向、运动控制和急停。只看到SP字节或串口打开不能判定导航通信通过。Ctrl+C结束本测试。

## 第四步：编译导航

确认目标机器已有可用的 `livox_ros_driver2` ROS包。仅有 Livox SDK 不等于 ROS驱动已构建。`build_nav.sh` 接收已有驱动工作区的 `install/setup.bash`，例如下列占位路径需按实际机器替换：

```bash
bash scripts/build_nav.sh /绝对路径/雷达驱动工作区/install/setup.bash
```

如果当前终端已经加载该驱动，可省略参数：

```bash
bash scripts/build_nav.sh
```

实车入口为 `src/rm_chassis_comm/launch/sentry_reality.launch.py`，完整说明见 `src/rm_chassis_comm/SENTRY_ARCHITECTURE.md`。本步骤只编译，不自动启动导航。

雷达IP、MID360/MID360S对应驱动参数、IMU单位、安装外参、云台零位和底盘许可均须使用本车实测值。仓库原实车参数含上游IP及MID360驱动配置，不能当作目标机器已验证参数。`geometry_confirmed`及电控许可默认关闭，保持直到完成标定和联调。

源码此前通过协议/坐标/ROS同进程PTY回归与ARM构建；这不等于目标电脑、物理USB、CAN或车辆已经验收。本次包仅增加交付脚本和说明，未改导航算法及电控原件。WSL中临时暂停校时和重启显示服务的处理不应照搬到原生Ubuntu。
