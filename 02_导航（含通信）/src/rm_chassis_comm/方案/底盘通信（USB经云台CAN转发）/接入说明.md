# 底盘通信（USB经云台CAN转发）

状态：网关与底盘端的无 HAL 接入封装，尚未并入本队固件或经过实车验证。文件同时提供云台网关 `rm_gimbal_gateway_*` 和底盘端 `rm_chassis_can_*`；两种上下文应分别放在对应板上。

## 两端职责

```text
PC 单一串口所有者 ⇄ USB CDC ⇄ 云台网关 ⇄ 经典 CAN ⇄ 底盘 MCU ⇄ 底盘仲裁和电机
```

云台网关只透传新协议完整帧：USB 的合法 `0x20/route=2` 命令原样分片，底盘生成的合法 `0x21/route=2` 反馈重组后原样送回 USB。网关没有 MCU 执行状态，不生成 READY/ACTIVE/ACK，不改 session、sequence、TTL 或任何速度字段。USB 成功送入 CAN 队列不代表底盘已收到；只有底盘真实反馈才可到达 PC。

底盘端完整重组、CRC 与载荷校验通过后才调用 `rm_mcu_receive`。错片、丢片、错路由、CRC 错误和超时中断都不能刷新 MCU 命令生命周期。底盘自己的周期任务检查 TTL、实际急停/人工模式和故障，调用 apply，再生成真实 MCU 反馈。

## CAN 传输约定

以下 ID 为**拟保留值，仍需电控核对实际总线分配**，不是从现有固件读到的已部署协议。

| 项目 | 约定 |
| --- | --- |
| 命令 CAN ID | 标准 11 位 `0x320`，云台→底盘 |
| 反馈 CAN ID | 标准 11 位 `0x321`，底盘→云台 |
| 帧 | 经典 CAN 数据帧，DLC 必须为 8；不使用扩展 ID 或 RTR |
| 字节 0 | 8 位 transfer_id，每次发送尝试递增并允许回绕 |
| 字节 1 | bit7 为最后片标志；bit0–6 为片索引，必须依次 0、1、2、3、4、5 |
| 字节 2–7 | 完整 34 字节 wire frame 的连续 6 字节片段 |
| 最后一片 | index 字节为 `0x85`；仅4字节有效数据，剩余2字节必须为0 |
| 超时 | 自首片起总计20ms；逐片到达不会延长期限 |

每个方向只保留一个固定大小的重组上下文。新 transfer_id 的首片可以替换未完成的旧尝试；同一 transfer_id 内重复、跳号、乱序、标志错误或混入其他 transfer_id 均丢弃。完整 CRC 及消息类型/route 校验完成后，MCU 还要做 session/sequence/watchdog 校验。CAN 的 transfer_id 不是控制命令序列号。

`rm_can_send_frame` 最多连续调用六次非阻塞发送回调。任意一次 BUSY/错误即结束本次发送，不再补发剩余片；下一次发送尝试使用新的 transfer_id。半帧会由对端顺序检查或总超时丢弃，不会更新运动命令。

**发送回调必须接有界、有序的 CAN TX 调度。** 不能简单地在一个循环中直接调用只有三个发送邮箱的 `HAL_CAN_AddTxMessage` 六次，否则通常在第四片遇 BUSY。应提供能接纳一帧六片的固定容量队列，顺序排出；总线邮箱优先级/发送顺序也须保证同一 CAN ID 的片序。队列不得无限积压过时控制命令，满时返回0，交给下一周期的新命令。CAN 接收中断同样应有界复制到单任务处理，不能与任务并发改写重组或 MCU 对象。

## 云台板接口

```c
rm_gimbal_gateway_init(&gateway, can_tx_copy, can_owner, usb_tx_copy, usb_owner);
rm_gateway_set_sp_handler(&gateway, handle_complete_sp_command, gimbal_owner);
rm_gimbal_gateway_usb_receive(&gateway, bytes, length);
rm_gimbal_gateway_can_receive(&gateway, id, extended, dlc, data, now_ms);
rm_gimbal_gateway_poll(&gateway, now_ms);
```

发送回调返回1表示已复制接受，0表示忙或失败。栈上帧指针不能被保存供异步传输。`poll` 仅处理重组超时，不替主机重造命令，也不不断重试旧命令。SP处理回调为可选项，接收完整29字节CRC正确且mode/角度/有限值检查通过的SP命令，仍由现有云台状态机决定是否接受目标。

## 底盘板接口

```c
rm_chassis_can_init(&chassis, can_tx_copy, can_owner, apply_chassis, motor_owner);
rm_chassis_can_set_safety(&chassis, ready, estop, manual_override, fault_mask);
rm_chassis_can_receive(&chassis, id, extended, dlc, data, now_ms);
rm_chassis_can_poll(&chassis, now_ms, measured_valid, measured_vx, measured_vy, measured_wz);
```

初始化的 ready=false，缺少 apply 回调也不能置为 ready。安全许可、控制权、导航模式与故障必须来自底盘实际状态。无收包时仍要在底盘控制任务中调用 `poll`，apply 必须处理 enabled=false；反馈按最多50Hz发送，BUSY丢本周期反馈。没有真实新鲜底盘速度时 measured_valid=false，不能拿目标速度充当测量。

## 本队固件需要补齐的落点

1. **云台工程不是底盘工程。** 现有 `云台_USB_SP_2026-10-28/.../basic_framework` 的 `GIMBAL_ONLY_BUILD=1`，底盘任务未运行，CMD 对底盘发布零力。网关只能把命令转交另一块已实现本协议的底盘板，不能使该云台固件本身具备底盘执行能力。
2. **需要真正的导航控制模式。** 当前底盘 `application/chassis/chassis.c` 的 NO_FOLLOW 会把 wz 清0，FOLLOW 重算 wz，ROTATE 生成自旋。接入处应增加明确的导航命令仲裁和保持三轴速度的模式，并由遥控/安全状态决定是否允许，不能假定已有模式就是导航模式。
3. **单位和坐标必须核定。** 新线协议固定 m/s、m/s、rad/s，车体系 x前/y左、wz逆时针。旧底盘注释是x前/y右，且先做云台offset旋转；旧运动学的轮速和转子rpm转换也未完整证明。需要电控核定参数与转换，避免多转一次坐标或把SI数值当旧电机参考值。
4. **CAN ID与物理口需核对。** 旧双板通信已有 `0x311/0x312`，电机、电容等也在使用CAN。新 `0x320/0x321` 必须检查冲突、HAL滤波、总线速率、端接及负载。旧内部 CANComm 的结构体传输不等同本分片协议。

## 与现有 SP 自瞄共享 USB

PC 侧必须只有一个物理串口所有者，同时处理新底盘帧与既有29/43字节SP帧；两个进程同时读同一个tty会抢走对方帧。配套主机节点提供可选PTY：视觉程序连接PTY，节点校验视觉29字节SP命令后与34字节底盘命令整帧调度到物理USB；从物理USB收到的43字节SP反馈再送到PTY。实际PTY参数以主机节点说明为准，视觉程序不能同时绕过PTY打开物理设备。

固件封装现在提供一个最多34字节的leading-magic分流器：按起始字节识别完整34字节新帧或29字节SP帧，CRC正确后整帧消费并分流，不让两套解析器并行搜索对方载荷。`rm_gateway_set_sp_handler` 把完整合法SP命令交给云台所有者，**不会**把新底盘帧交给存在长度问题的旧Seasky解析器。

SP遥测发送应改接 `rm_gimbal_gateway_send_sp_status(&gateway, frame43)`，它校验CRC并与底盘反馈共用同一个 `usb_tx_copy` 所有者。共享发送回调负责固定容量队列和CDC忙管理，两个任务不能直接争用同一个CDC端点。现有 `master_process.c`、USB BSP 和任务调用的实际改线仍需电控集成；提供分流回调不等于本包已自动完成自瞄接管和硬件适配。

现有SP本身没有vx/vy/wz字段，不能在43字节后直接追加字段。旧Seasky也不能仅靠换cmd_id接收新速度包。应在公共传输所有者层增加明确的分流和有界队列，再分别调用各自codec和业务模块。

## 验收

- 无HAL测试先检查六片、乱序、丢片、错误CRC/路由/类型、20ms边界、计时回绕与BUSY中断。
- 无运动联调确认云台不产生ACK；断开CAN后，PC应收不到有效底盘新反馈，底盘本地仍按TTL停止。
- 在完整反馈返回后检查session/sequence回显，再验证人工接管、急停、模式切换与丢包停止。
- 最后由电控受控核对速度符号、SI转换、导航wz不被覆写和实测速度反馈。
