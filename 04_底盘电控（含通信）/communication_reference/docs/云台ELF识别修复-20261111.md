VS Code 当前打开 `gimbal_firmware/` 子目录，原 ELF 在同级的 `artifacts/` 下，超出了当前工作区。尝试通过 EmberProbe 官方配置接口选择原文件时，接口明确返回 `PATH_OUTSIDE_WORKSPACE`，不能直接把上一级文件用于这个工作区。

## 使用哪个工程、哪个文件

VS Code 使用「文件 → 打开文件夹」打开：

```text
/home/wangjiaming/桌面/c_board_nav_gateway_20261111/gimbal_firmware
```

EmberProbe 的「选择 ELF 固件」应为：

```text
/home/wangjiaming/桌面/c_board_nav_gateway_20261111/gimbal_firmware/firmware_release/gimbal_nav_converter.elf
```

这是要烧进**云台 C 板**的文件，对应 USB → 云台 CAN1 ↔ 底盘 CAN2，两端 CAN 均为 1 Mbps。默认禁止电机运动输出。

同目录的 `gimbal_nav_converter.hex` 是相同程序的 HEX 格式，供其他支持 HEX 的工具使用。EmberProbe 选择 ELF；无需将 ELF 当文本文件打开，也无需复制 HEX 内容到编辑器。二进制文件无法在文本编辑器显示，不代表 ELF 损坏。

## 烧录状态与待确认

**ELF 配置成功不等于已经烧录成功。**

现场窗口中的最近下载记录显示 `CMSIS-DAP command CMD_INFO failed`、退出码 1；这是下载器查询未成功，与当前 ELF 文件有效性是两个问题。本轮未执行擦除/写入，也未把下载失败写成烧录成功。之前 USB 双向正常、底盘 ACK 为 0 帧的测试结论仍需待真正烧录和 CAN 链路排查后复测。

本轮配置读回曾成功；后续只做下载预检查时，Bridge 又返回 `BRIDGE_UNAVAILABLE`、`registryEntries=0`，导致预检查降级到默认系统 OpenOCD 0.11.0，`ready=false`。该降级输出不代表用户已保存的 0.12.0 设置被更改。需要在本云台工程保持 EmberProbe 激活/Agent 访问，重新读取配置成功后才能判断下载前提，不应据此盲目重装固件库或修改 ELF。

待确认项：实际下载器是否稳定回复、芯片身份与板内 Flash 校验、新版是否写入成功、云台 CAN1 到底盘 CAN2 的双向 ACK。下一次下载应沿用用户确认的 SWD 接云台、电机主电源断开、目标板和无线接收端有正确供电；如实物接线变化需先重新核对。
