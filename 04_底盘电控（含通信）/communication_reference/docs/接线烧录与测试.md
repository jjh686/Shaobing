# 接线、分别烧录与通信测试

日期：2026-11-11。适用交付目录：`/home/wangjiaming/桌面/c_board_nav_gateway_20261111`。

## 1. 实际链路

```text
MID-360S ──以太网── 小电脑：新导航、定位、路径规划
                          │ USB 数据线
                          ▼
                    云台 C 板：解析 USB、转换 CAN
                          │ 云台 CAN1 ↔ 底盘 CAN2，H/L + GND
                          ▼
                    底盘 C 板：检查命令、遥控器、电机状态
                          │ CAN1
                          ▼
                    C620 × 4 → M3508 × 4
```

雷达的点云、障碍物处理和路径规划在小电脑上运行。小电脑输出底盘速度目标，云台板负责通信转换，底盘板负责电机闭环。雷达继续按此前配置以太网连接小电脑，雷达供电独立处理；本次没有更改其网络配置。

两块 C 板之间使用 **云台 CAN1 ↔ 底盘 CAN2，1 Mbps，标准数据帧、DLC=8**。本工程芯片映射：云台 CAN1 RX=PD0、TX=PD1；底盘 CAN2 RX=PB5、TX=PB6。实物接线使用板载收发器后的 CANH/CANL 接口，不直接连接 MCU RX/TX 引脚。CAN1/CAN2 是各板的本地控制器编号，两端编号可以不同。

| 云台板接口 | 底盘板接口 | 说明 |
|---|---|---|
| CAN1 H | CAN2 H | H 对 H |
| CAN1 L | CAN2 L | L 对 L |
| GND | GND | 共参考地 |
| 板载 Micro-USB 数据口 | 小电脑 USB | 云台板的物理 USB 通信口 |

按板上丝印、原理图确认针序，不能按排线颜色或插头方向猜测。CAN 插头可能包含电源脚，不要把两个电源输出互接。两板各自由合适的分电板电源输入供电；电池电压不能接入 USB 或 SWD 信号脚。

CAN 总线两个物理末端各一个 120Ω 终端。先确认板载终端是否已存在；断电测 H/L 间约 60Ω 是两只 120Ω 并联的典型结果，不应重复加满终端。初次联调用短双绞线，避免星形接法。

底盘四个 C620 接底盘板 CAN1，ID 对应为左前=1、右前=2、左后=4、右后=3。接收机接**底盘板 USART3/SBUS**。固件按原工程的 FS/SBUS 解码配置为 100000 baud、8 数据位、偶校验、1 停止位（HAL 配置 9B+偶校验）；接收机电平、反相条件和通道映射需实机核对。

云台 CAN1 专用于板间导航中转；保留的云台电机实例改到云台 CAN2，当前仍关闭执行输出，发射任务不启动。以后恢复云台电机前需要按新分配确认其物理接线与 ID。本次通信测试无需连接云台电机。板间导航 ID 为 0x330～0x332、0x338～0x33A，必须避免其他设备使用相同 ID。

## 2. 两块板分别烧录

本目录已生成固件；实际烧录结果见《本轮烧录与测试文档记录》和《云台CAN1到底盘CAN2改动说明》，不能把本节操作步骤当作已执行记录。

1. 在电机主电源断开的条件下，给目标 C 板和下载器正确供电。
2. 下载器通过 SWDIO、SWCLK、GND 连接**当前要烧录的那一块 C 板**。目标电压检测端与供电输出端的用途按下载器手册确认，避免两路电源互顶。
3. 当前 MuseLab CMSIS-DAP 使用 EmberProbe/OpenOCD 连接 STM32F407，先备份可读原固件，再烧录并校验 HEX/ELF。EmberProbe 需要 OpenOCD >= 0.12.0。STM32CubeProgrammer 的 SWD 下载通常使用 ST-LINK，不能把当前 CMSIS-DAP 当作 ST-LINK 选择。
4. 云台板烧入 `artifacts/gimbal_nav_converter.hex`；底盘板烧入 `artifacts/chassis_nav_can.hex`。BIN 若按地址烧录，起始地址为 `0x08000000`。
5. 烧录完成后按各板正常 Flash 启动配置恢复 BOOT、复位，再接应用 USB/CAN。

USB 连云台板、CAN 连底盘板的结构**不会自动替另一块板烧录**。本项目没有实现 CAN bootloader，底盘板也需要单独连接下载器。无线 SWD 下载器的 USB 发射端属于调试设备，不能替代云台 C 板自身的应用 USB 串口。

## 3. 先做零速度往返检测

停止其他占用 C 板物理串口的程序，只运行一个测试入口：

```bash
ls -l /dev/serial/by-id/
bash /home/wangjiaming/桌面/c_board_nav_gateway_20261111/pc/run.sh zero /dev/serial/by-id/实际云台板设备名
```

脚本验证 VID/PID 为 `0483:00ca`、产品名为 `RM Nav Convert SP`，因此旧测试固件、自瞄旧固件和下载器会被拒绝。USB 枚举完成仍只证明电脑与云台 USB 接通；必须收到本次会话的新鲜底盘 ACK，才证明双向 CAN 链路也工作。

脚本以 50Hz 发送新会话的 STOP，持续约 5 秒，不会发送 ENABLE。成功条件包括收到至少 10 帧新鲜 ACK、会话和序列号对应、底盘 uptime 前进、结束时反馈未过期。默认固件的 LOCK/UNITS 故障是预期结果；没有遥控器或电机时还会报告对应故障，通信测试仍可通过。

排查顺序：

- 没有 `/dev/serial/by-id`：检查云台板供电、数据线、正常 Flash 启动及固件烧录校验。
- 产品名不符：确认 USB 接的是云台 C 板自身，且已烧入本次转换固件。
- USB 识别正常但无底盘 ACK：核对两块板固件、云台 CAN1/底盘 CAN2 接口、H/L/GND、波特率、终端与 ID 冲突。
- ACK 正常但 READY=0：按 `fault` 故障位检查运动锁、轴向确认、遥控器和电机。

## 4. ROS 通信模式

零速度脚本退出后启动：

```bash
bash /home/wangjiaming/桌面/c_board_nav_gateway_20261111/pc/run.sh comm /dev/serial/by-id/实际云台板设备名
```

该模式调用已配置的新导航包 `rm_chassis_comm/chassis_node`，命名空间 `/chassis`，速度输入是车体系 `/chassis/manual_body_cmd_vel`（`geometry_msgs/msg/Twist`）。这是车体系通信联调入口，不包含云台坐标系转换或完整 Nav2。

另开终端加载新导航环境后查看反馈：

```bash
source '/home/wangjiaming/桌面/rm_nav_source_20261110(zbh)/scripts/local_env.sh'
ros2 topic echo /chassis/diagnostics
ros2 topic echo /chassis/measured_velocity
```

电机没有真实反馈时，节点不会用“假零速度”代替实测值。通信心跳可通过 diagnostics 查看。

SP 自瞄程序通过此节点创建的虚拟串口接入：

```bash
ros2 topic echo /chassis/sp_proxy --qos-durability transient_local --once
```

把输出的 `/dev/pts/N` 配置给视觉程序；每次节点重启路径可能变化。物理 C 板 USB 口由 ROS 通信节点独占，视觉程序不能再同时打开该物理口。原 SP 命令 29 字节、状态 43 字节的格式保留。

## 5. 允许轮子运动前要完成的配置

此次 HEX 中底盘 `NAV_RELAY_ALLOW_MOTION=0`、`NAV_AXES_VERIFIED=0`，云台 `GIMBAL_INSTALLATION_CONFIRMED=0`。收到非零速度也不会放开运动输出。

底盘受控测试前，需要核对四轮 ID、转向、轮径、减速比、轴距、轮距及 ROS 的 X/Y/旋转正方向。`chassis_firmware/modules/nav_relay/nav_relay_config.h` 中三个 `*_SIGN` 为理论值 +1；完成实测后再填写方向、设置 `NAV_AXES_VERIFIED=1`，明确准备测试时设置 `NAV_RELAY_ALLOW_MOTION=1`，重编译并只重烧底盘固件。构建脚本不会自动替你开启这些开关。

底盘运动还要求：遥控器在线、CH7/CH8 的两个开关均明确处于中档、四电机反馈在线、无接收故障，并完成 STOP 握手。非法开关值不会被当成中档。遥控器离线、退出中档、反馈离线或 TTL 过期都会移除输出；恢复后必须重新 STOP 握手并重新使能。

完成上述实机确认后，在 ROS 通信模式中才可人工申请使能：

```bash
ros2 service call /chassis/set_enabled std_srvs/srv/SetBool '{data: true}'
```

使能服务成功后，节点只接受随后新到的速度，不沿用使能前的命令。车体系台架测试应从很小速度开始，例如持续发布 X=0.03m/s，观察实际方向和停机动作：

```bash
ros2 topic pub --rate 20 /chassis/manual_body_cmd_vel geometry_msgs/msg/Twist '{linear: {x: 0.03, y: 0.0}, angular: {z: 0.0}}'
```

停发布会触发速度超时；也可显式取消使能：

```bash
ros2 service call /chassis/set_enabled std_srvs/srv/SetBool '{data: false}'
```

## 6. 完整新导航入口与当前限制

```bash
bash /home/wangjiaming/桌面/c_board_nav_gateway_20261111/pc/run.sh navigation /dev/serial/by-id/实际云台板设备名
```

该入口转到新导航包原来的 `scripts/run_sentry.sh navigation`，命名空间为 `/red_standard_robot1`，保留带时间戳的云台→车体速度转换、有效关节角门控和 `frame_ready` 门控。不能和 `comm` 或 `zero` 模式并行占用同一个 USB。

当前云台固件只回传 `status=0` 的无效关节诊断包，没有声称具备已标定关节角。此前新导航配置中的 `geometry_confirmed=false` 也保留。因此该命令可进入现有启动流程，但**完整导航运动仍会被门控阻止，不能据此宣称已具备实车自主导航**。

后续要补齐底盘相对的真实 yaw/pitch 编码器零位、方向、安装转轴位置和关节采样路径。IMU 世界航向、自瞄 SP 的姿态、上电相对角度都不能直接代替底盘相对的已标定关节角。详见《改动与待确认》。
