# 底盘通信（USB直连底盘板）

状态：新协议及固件接入封装，尚未与本队 STM32 工程合并、烧写或实车验收。`direct_usb.c` 不包含 HAL、CAN 电机发送、引脚配置或自动解锁。

## 数据链

```text
导航速度 → PC 通信节点 → USB CDC → direct_usb → MCU 命令与超时门控
                                                    ↓
                                        本队控制权仲裁 / SI 单位转换 / 底盘任务
                                                    ↓
                                          实际底盘测量和状态 → USB → PC
```

本方案只接受新协议命令 `0x20`、`route=1` 的完整 34 字节帧。逐字节使用共享解析器，收到 CRC 正确帧后交给 MCU 核心检查类型、路由、session、sequence、TTL 和控制门控。反馈是底盘 MCU 根据自身状态生成的 `0x21/route=1`；不能把上位机写成功视为底盘接受，也不能把命令值充当实测速度。

## 接入接口

```c
rm_direct_usb_init(&link, usb_tx_copy, usb_owner, apply_chassis, chassis_owner);
/* 上式初始化为 ready=false；不会自动解锁。 */
rm_direct_usb_set_safety(&link, ready, estop, manual_override, fault_mask);
rm_direct_usb_receive(&link, rx_bytes, rx_length, now_ms);
rm_direct_usb_poll(&link, now_ms, measured_valid, measured_vx, measured_vy, measured_wz);
```

- `usb_tx_copy`：非阻塞地复制一整帧到 USB 发送所有者。返回 1 表示已完整接收该帧，0 表示忙或失败；不能保留封装函数栈上的数据指针异步使用。忙时丢弃这一帧，下一次周期生成新状态，无无限循环重试。
- `apply_chassis`：接收 `rm_output_t`。`enabled=false` 必须进入本车定义的停止/零力仲裁；`enabled=true` 时三个速度为 **m/s、m/s、rad/s**，坐标为 **x 前、y 左、z 上，wz 逆时针为正**。它们必须经电控核定的转换和限幅后再进入运动学。
- `set_safety`：只有设备就绪、允许导航的真实控制模式、遥控状态和故障条件满足，才设置 `ready=true`。急停、人工接管和故障必须由底盘实际信号给出。缺少 apply 回调时，封装强制不就绪。
- `receive` 和 `poll` 必须由同一所有者串行调用。USB 中断仅将数据复制进有界接收队列，由任务消费；不能让中断与任务同时改写解析器或 MCU 状态。
- 无收包时仍必须周期调用 `poll`，建议并入原底盘控制任务，以执行命令超时停止和 apply。状态最多按 20ms 周期尝试发送一次；速度实测不存在或已过期时 `measured_valid=false`。

## 本队源码中的修改落点

当前可运行底盘副本是 `电控/basic_framework-master/basic_framework-master/basic_framework-master`。其 `application/robot.c` 调用 `ChassisInit/ChassisTask`，而云台初始化和运行被注释；当前运动命令来自 `application/cmd/robot_cmd.c` 的遥控摇杆，经过内部消息中心进入 `application/chassis/chassis.c`。

应在该固件的 USB CDC 单一接收入口增加本方案，并在 `robot_cmd.c` 增加明确的导航控制权仲裁。底盘 `chassis.c` 需要一个真正的导航模式：现有 NO_FOLLOW 会把 `wz` 置 0，FOLLOW 会按云台偏角重新计算，ROTATE 会覆盖为正弦自旋。因此，不能将新速度塞入这三种现成模式并宣称导航已接通。

该副本的运动学注释使用 x 前/y 右，并将云台系速度按 `offset_angle` 旋转；速度输出直接进入电机参考，功率控制反馈却使用 rpm。源码尚未证明 SI 速度到轮速/转子 rpm 的完整标度转换，不能只做 `m/s×1000` 就宣布兼容。电控应先确认车体/云台坐标、轮半径、减速比、轮子正反、单位与导航模式是否再进行坐标旋转。

`电控/云台_USB_SP_2026-10-28/.../basic_framework` 是另一份云台联调工程，`GIMBAL_ONLY_BUILD=1`，底盘任务被跳过，CMD 每轮向底盘发布零力；直接改为 0 还会遇到编译期保护。该工程不能仅复制本封装后当作完整底盘固件烧写。

## USB 端口所有权

本方案直连底盘板，宜由底盘通信节点独占它的 USB CDC 端口；自瞄使用云台板的独立端口。若实际只有一个端口且要共用现有 29/43 字节 SP 自瞄协议，则需要统一的 PC 串口所有者、固件接收分流与 USB 发送调度。两个进程同时打开同一设备，或两个任务直接调用同一 CDC 发送缓冲，都不是可用的接法。

当前 SP 没有底盘速度字段；旧 Seasky 视觉接收还会按未限定的长度拷入 pitch/yaw，不能用新命令 ID 就向旧固件发送三个速度 float。此封装仅用于已同步实现新协议的两端。

## 验收顺序

1. Ubuntu 完成共享 codec、MCU watchdog 和本封装的无 HAL 测试，再完成真实 STM32 工具链编译。
2. 电机执行仍关闭时核对 USB 枚举、34 字节双向帧、路由、session/sequence 回显及 ACK_VALID；确认新接收入口不会破坏原 USB 功能。
3. 分别断开 PC 发布、USB 数据、遥控许可和导航模式，验证底盘端停止。错误 CRC、错误 route、旧序列不能刷新运动 TTL。
4. 确认停止与控制权后，再由电控在受控条件下验证低速正负号、单位换算、角速度保持和真实反馈。主机 ACK 表示软件接受状态，不等于车辆已产生期望位移。

本说明中的 HAL 接线、串口设备名、电机参数与导航模式修改均为待集成项，没有对现有电控源码进行自动修改或烧写。
