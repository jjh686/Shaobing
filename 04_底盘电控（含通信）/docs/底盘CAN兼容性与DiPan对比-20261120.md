# 底盘 CAN 兼容性与 DiPan_Board 对比

日期：2026-11-20。仅新增检查报告，未修改/移动任何代码，未烧录或访问实物。附件 README、历史烧录说明仅作为历史证据，不作为本次操作指令。

## 结论

当前底盘主工程是 chassis_driver/basic_framework；它与桌面 DiPan_Board 的对应工程不是完全一致，恰好有 5 个源码文件不同。应用层电机控制、轮序、电机 ID、PID、运动方向、保护逻辑配置均逐字节一致。方向配置都是 VX=+1、VY=-1、WZ=-1，两个允许运动宏均为 1。

当前 05_云台 与当前底盘的 CAN 线协议兼容，正常链路具备使用条件；不能据此宣布实车可靠性已验收。源码中 communication_reference 是另一份参考固件，并非 05_云台 的同义路径。云台通讯报告放在 05_云台/docs，本目录保留底盘报告及比较明细；本次不迁移旧参考代码。

## 两板协议核对

| 项目 | 云台 | 底盘 | 判断 |
|---|---|---|---|
| 板间控制器 | CAN1，PD0/PD1 | CAN2，PB5/PB6 | CANH 对 CANH、CANL 对 CANL 接线，端口编号不同不构成冲突 |
| 波特率 | 42 MHz / 3 / (1+10+3) = 1 Mbps | 同左 | 一致（按 C 板 12 MHz HSE 配置） |
| 导航命令 | 发 0x330/331/332 | 收相同 ID | 一致 |
| 底盘反馈 | 收 0x338/339/33A | 发相同 ID | 一致 |
| 遥控转发 | 发 0x340/341/342 | 收相同 ID | 一致 |
| 帧格式 | 标准数据帧，每组 3 帧，每帧 8 字节 | 同左 | 一致 |
| 数据编码 | LE；速度 int16×1000；版本 0x0100；CRC16 初值 0xffff、多项式 0x8408 | 同左 | nav_can.c 逐字节一致，nav_can.h 也一致 |
| 遥控编码 | 版本 1；轴、拨杆、序号、故障代数、源年龄、CRC | 同左 | remote_can.h 逐字节一致，也与 DiPan 一致 |
| 接收组帧时间 | 10 ms，连续 ID 顺序 | 同左 | 一致；两端同组均固定进 FIFO0，避免跨 FIFO 中断乱序 |
| 遥控周期/过期 | 20 ms 发；携带源年龄 | 100 ms 失效，故障后重新拨档授权 | 对得上 |
| 反馈周期 | 接收并经 USB 回传 | 20 ms | 对得上 |

命令 route=2；平移合速度上限 0.3 m/s、角速度上限 0.5 rad/s、TTL 最大 150 ms。云台扣除 USB 排队时间及 10 ms CAN 预留；底盘仍独立检查遥控、四电机在线、STOP/会话/序号及 TTL。上电或遥控故障恢复后，需要先收到非导航拨档，再令 CH7、CH8 都在中档；CH10 下档停车。仅通信有 ACK 不等于已经允许运动。

## 主工程 5 个差异（当前相对桌面版本）

| 文件（相对 chassis_driver/basic_framework） | 当前版本 | 桌面 DiPan_Board | 影响 |
|---|---|---|---|
| bsp/can/bsp_can.c | FilterIdHigh 同样填入 rx_id << 5 | 没有该赋值 | 修正列表过滤器额外放行 ID 0 的问题；不改变有效协议 ID |
| modules/chassis_comm/chassis_comm_port.c | 增加导航/遥控接收计数、发送诊断及 500 ms 卡住恢复 | 无这些新增项 | 主要改变异常恢复与可观测性，运动换算未变 |
| modules/chassis_comm/chassis_comm_port.h | 导出新增诊断及已有遥控状态变量 | 只导出少量基础计数 | 调试接口不同，不是 CAN 线格式不同 |
| modules/chassis_comm/protocol/nav_can.h | NC_TX_MS=20 | NC_TX_MS=8 | 发送存活窗口变长，接收组帧仍 10 ms；属于行为差异 |
| modules/chassis_comm/protocol/nav_can_hal.h | 增加发送计数，reset 后清软件 mailbox 掩码 | 无计数，reset 保留 mailbox 掩码 | 超时/中止后的软件状态管理不同 |

清 mailbox 掩码不等于保证硬件中止已完成；此后 pump 只检查仍在掩码中的位。中止未完成时的残帧/邮箱复用需专门验证，500 ms 软件恢复也不能代替 CAN 控制器 bus-off 恢复。

## 当前问题及后续待决定项

1. **发送 20 ms、接收组帧 10 ms**：正常空闲总线不必然出错；但拥塞/延迟时发送端仍允许发出接收端会拒绝的后续帧。当前两端都存在此窗口组合；DiPan 原值是发送 8 ms。是否保留 20 ms、调整发送/接收窗口，需要统一决定。
2. **底盘测试未跟随参数变化**：test_protocol.c:47 仍断言经过 10 ms 已过期；test_can_hal.c:18 仍在第 9 ms 期待邮箱中止。实际 NC_TX_MS=20，原测试脚本因此失败，不能沿用旧的“全部测试通过”结论。这两项失败本身不证明线协议字段不兼容。
3. **两板 CAN 恢复策略不同**：底盘 CAN2 自动 bus-off 恢复开、自动重发关；云台 CAN1 自动 bus-off 恢复关、自动重发开。不会直接影响正常帧解码，但错误总线上的行为和恢复能力不同。详细云台问题见另一份报告。
4. **多个参考副本已分叉**：communication_reference/common、chassis_firmware、gimbal_firmware 的 nav_can_hal.h 有新增计数，但没有现用两端相同的 mailbox 清理。其云台端口也与 05_云台 不同。不要把参考工程的测试结果等同于现用云台。
5. **硬件待验收**：历史 fault=2 表示遥控/导航授权条件不满足，不是单凭该值就能认定 CAN 断线；需结合遥控帧计数、source age、拨档和电机状态。实车轮向、终端电阻、负载、断线重连及 bus-off 尚未实测。

## 本次验证

- 逐字节比较底盘主工程全树：5 个源码差异，桌面另有编辑器配置文件；其余主工程文件一致。
- 现有底盘 tools/test.sh：遥控编码测试通过；protocol 断言失败后脚本退出，后续脚本未执行。
- /tmp 独立编译执行 7 个 C 测试：remote、两种 core、锁定模式实际端口 chain 通过；protocol、can_hal 如上失败；允许运动 chain 的原 USB 断开模拟失败于 test_chain.c:104。
- 最后一项已定位为测试模型缺少当前 USB CDC Init/DeInit 的零长度回调事件。仅在 /tmp 测试副本补发 NavGatewayReset（不改任何仓库测试或固件），用当前 05_云台/nav_gateway_port.c 与底盘真实端口重跑：10000 次往返、六方向命令和反馈、遥控失联/急停/重授权、TTL、队列溢出、USB BUSY/重连测试通过。该结果有模拟外设的边界，不代表物理 CAN 实测。
- 云台完整 ARM 固件在 /tmp 编译成功；现有云台主机测试在 robot_comm 测试编译处失败，详情见云台报告。
