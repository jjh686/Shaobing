# 遥控通信分段测试步骤（2026-11-16）

## 先确认已经知道什么

11月14日已验证：小电脑USB→云台CAN1→底盘CAN2的STOP链路能持续往返；CH7和CH8的三个档位能传到底盘。双中档曾使导航许可变成1，随后在开关保持不动时，云台遥控源故障代数从41增至45，底盘撤销许可并保持fault=2。

所以现在优先检查“遥控器无线→接收机S.BUS→云台UART3解析”。板间CAN仍需要对照记录，但旧观测中底盘CAN错误寄存器为0、遥控CAN拒绝组为0，不能把fault=2直接认定成CAN线不通。

11月16日本轮只核对代码、设备列表并准备步骤，未连接MCU读取、未烧录、未发送速度。当前只识别到MuseLab下载器，未识别到云台应用USB；用户选择稍后接线再现场测试。本文件是待执行方案，不是新的实测通过记录。

## 第一阶段：电机断电，单独验证遥控源

1. 断开四个C620的电机主电源，停止导航、通信节点和motor_test；保留两块C板正常外部供电。四轮继续架空。
2. 接收机保持原S.BUS输出设置，信号接云台C板DBUS（UART3板载反相路径），电源和地按已确认接线；不得把普通PWM输出当作S.BUS。不要在通电时改线。
3. 小电脑USB接云台C板自身Micro-USB；云台CAN1接底盘CAN2，H对H、L对L、公共地保留。
4. SWD接云台板，在EmberProbe确认当前芯片末尾36363032；选用与板内程序匹配的云台ELF。此前底盘芯片末尾31353233，不能沿用底盘ELF读取云台变量。
5. 云台ELF候选在 `artifacts/Gimbal_USB_CAN1.elf`，但不能仅因路径存在就认定与板内一致；需先核对部署/烧录记录和匹配状态。没有匹配证据时先保留未知，不盲目重刷。

本阶段电机断电，四电机不在线，`fault=4`是预期结果。应观察遥控相关位2是否消失、源故障计数是否稳定；不能把“fault必须为0”作为本阶段的通过条件。

## 第二阶段：遥控保持不动，记录60秒，重复三轮

遥控器和接收机正常供电、天线位置正常、相距约1～2米；不触碰导线，不操作任何摇杆/开关，CH10保持非下档。CH7或CH8先离开中档保持1秒，再将CH7和CH8都回到中档。每轮建立基线后保持60秒，不通过持续切档掩盖故障。

需要两处记录，不要把SWD在通电时随意来回插拔：

| 观测点 | 要记录的内容 | 用途 |
|---|---|---|
| 云台SWD | `fs_fault_generation`、`fs_fault`、`fs_last_valid_tick`、`fs_rc_ctrl`，以及 `nav_rc_online`、`nav_rc_estop`、`nav_rc_age_ms`、`nav_rc_groups` | 直接判断云台接收到的遥控源是否稳定 |
| 电脑USB底盘反馈 | 新鲜底盘ACK、fault及变化、status | 确认许可有没有在整条链路上掉落 |
| 后续必要时底盘SWD | `chassis_rc_online/navigation/estop`、`remote.generation/off_seen/armed/rejected`、`chassis_comm_can_esr` | 区分源故障、CAN组错误和底盘重新使能保护 |

`fs_fault_generation`绝对值非0不表示当下必然故障；看静止阶段是否继续增加。代数不变不等于线上没有任何丢包，仍要对照年龄、在线状态和后续专项测试。

现有固件把多类源故障汇总到一个计数，无法仅凭该值分出具体原因。`huart3.ErrorCode`可能被HAL后续恢复流程清零，单次读到0也不能排除历史串口错误。

### USB设备与零速度记录命令

先检查设备：

```bash
cd /home/wangjiaming/桌面/DiPan_Board
ls -l /dev/serial/by-id/
```

需要出现云台应用设备 `usb-YueLuEmbedded_RM_Nav_Convert_SP_3668306E3533-if00`。`usb-muselab-tech.com_CMSIS-DAP-MuseLab_0001A0000002-if00`是下载器，不能代替应用通信USB。不要固定写ttyACM0，因为编号可能变化。

确认设备存在后：

```bash
cd /home/wangjiaming/桌面/DiPan_Board
PORT=/dev/serial/by-id/usb-YueLuEmbedded_RM_Nav_Convert_SP_3668306E3533-if00
RUN_ID=$(date +%Y%m%d-%H%M%S)
bash tools/zero_test.sh "$PORT" --duration 60 --report "logs/rc-static-$RUN_ID.json" > "logs/rc-static-$RUN_ID.log" 2>&1
cat "logs/rc-static-$RUN_ID.json"
python3 tools/summarize_rc_log.py "logs/rc-static-$RUN_ID.log"
```

以上命令全程仅发送禁用STOP。每轮重设RUN_ID后重复，保存不同日志。脚本PASS只表示新鲜底盘STOP ACK通过；另看fault是否含2，源故障代数是否增加。不要同时运行导航串口节点或motor_test。

诊断阶段预期：四电机断电但遥控正常时，fault通常为4；若fault=6，表示同时有遥控许可问题2和电机离线4。带电且四电机在线后，遥控及其他条件均满足时才要求fault=0、STOP状态status=73。

## 第三阶段：根据哪个计数增加来定位

| 现象 | 优先排查 |
|---|---|
| 云台源故障代数增长，板间CAN无错误 | 遥控无线、接收机供电、S.BUS线、云台UART3接收/解析 |
| 云台源稳定，但底盘遥控CAN拒绝数/接收错误增长 | 板间CAN接线、终端、供电共地、队列/组帧及调度 |
| 源稳定、CAN无错误、CH7/CH8并非双中档 | 实际通道映射及遥控开关设置 |
| 源稳定、双中档，但off_seen=0 | 上次故障后尚未收到有效非导航样本，按退出再进入顺序操作 |
| 源故障后又恢复在线，双中档但许可仍为0 | 正常恢复保护；先修复不稳定源，再重新切档 |

当前源码可能增加源故障代数的条件：接收长度不是25字节、SBUS头尾不合法、frame-lost/failsafe标志、开关值不在有效范围、有效帧超过100ms未到、CH10停止。必须把这些原因分开计数，才能有针对性地修改。

### 若需要新增诊断固件

先保存现有ELF/HEX/BIN及SHA256，在云台加只读诊断计数，再编译、按具体计划确认烧录；不能把“准备增加”当作“当前已经有这些变量”。建议至少记录：

- 总接收事件数、真正有效SBUS帧数；短帧/长度错误、头尾错误各自计数。
- frame-lost、failsafe分别计数。
- CH7、CH8、CH9、CH10原始11位值和非法档位计数；当前代码没有统一保存这些原始值供独立统计。
- 连续有效帧的最大时间间隔、超过100ms计数。
- UART3奇偶校验、帧错误、噪声、溢出计数及DMA重启失败。
- 最近一次故障原因、时间、原始25字节，以及CH10软件停止计数。

当前UART3源码是100000波特率、8个有效数据位、偶校验、2停止位（HAL字长9B包含校验位），DBUS有板载反相。若实测串口异常，需要对照接收机S.BUS说明和实际烧录程序；不能只凭源码认定板内配置，也不要任意改成无校验或绕开反相。

DMA/IDLE每次回调不一定总是一帧完整SBUS。若长度/头尾错误占主导，要排查25字节DMA边界、帧对齐和丢字节恢复；若接收机明确报告frame-lost/failsafe，应优先查无线链路和接收机，不应通过忽略标志来让fault看起来稳定。

## 第四阶段：硬件对照，每次只改一个条件

保持电机断电，各做相同60秒记录并保存：

1. 正常供电、固定短S.BUS信号线、不动开关，建立基线。
2. 遥控器电池正常、接收机天线按厂家要求布置，避开金属遮挡和强干扰源；不要把发射天线紧贴接收天线。
3. 断电后核对/更换S.BUS线，检查信号/地接触。测量接收机额定电源在接收机端是否稳定；有条件用示波器看瞬态压降，单看指示灯亮不能证明供电稳定。
4. 如有同型号已知正常接收机或遥控器，按正确对频流程替换一个部件后再测。外接稳压电源须符合接收机额定电压、共地，不能与板载5V输出直接并联。

只做一个条件的改变，才能判断哪个改动使故障消失。未核对针脚前不按线色猜测电源极性。

## 第五阶段：验证停止与恢复（仍不给电机上电）

静止三轮稳定后，逐项测试，每项独立记录：

| 操作 | 应看到的结果 |
|---|---|
| CH7或CH8退出中档 | 导航许可撤销，fault含2；双中档按恢复顺序进入后恢复许可 |
| CH10下档再释放 | 撤销许可；释放不能自动恢复，需退出导航档再进入 |
| 关闭遥控器后再打开 | 云台收到failsafe/失联或有效帧超时后撤销许可；恢复不能自动重新使能 |
| 断电后拔接收机信号，再给C板上电 | 源保持离线、导航不许可；恢复接线前再次断电 |
| 断电后断开板间CAN，再给两板上电 | 底盘遥控数据失效、不给许可；USB底盘ACK可能完全收不到 |

现有超时约100ms，但软件调度和反馈采样有额外延迟，不能根据低频SWD抽样宣称实物停止耗时恰好100ms。若要求测停止延迟，需要高频计数或示波器/逻辑分析仪时间证据。

## 第六阶段：架空通电与电机测试

只有静止稳定性和停止/恢复测试通过后才做。停止所有占用USB的节点，四轮架空、现场准备电机断电开关。

1. 给四个C620正常上电，先不发ENABLE；做60秒STOP对照，确认源故障计数不增加、fault持续0。若只在C620通电后变差，优先检查电源压降、公共地、信号布线和电磁干扰。
2. 确认四个ID为左前1、右前2、左后4、右后3，四电机CAN反馈均在线。
3. 重新建立遥控导航许可，先发0.05m/s、1秒前进测试：

```bash
cd /home/wangjiaming/桌面/DiPan_Board
PORT=/dev/serial/by-id/usb-YueLuEmbedded_RM_Nav_Convert_SP_3668306E3533-if00
bash tools/motor_test.sh "$PORT" --wheels-raised --direction forward --duration 1
```

4. 核对每个轮子的实际运动和脚本STOP确认，方向异常、抖动、许可掉落立即停止并断开电机主电源。再按11月14日电机测试文档逐方向验证，之后才进行落地导航。

不要取消失控保护、强制写armed或只扩大超时来隐藏错误。fault=0表示固件当前许可条件满足，不能替代遥控停止链路、机械方向和实车控制验证。
