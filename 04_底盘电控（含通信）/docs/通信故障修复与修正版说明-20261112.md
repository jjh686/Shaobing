此前 5 秒实物检查中，电脑成功打开应用 USB；发送 226 个 STOP 命令，收到 54,589 字节数据，解析到 1,001 帧旧 SP 遥测和 251 帧云台遥测。云台最后回报的 session=1631623793、sequence=225，与本次发送相符，说明 USB 上行解码和下行回报已有实际证据。

但是，没有收到有效的底盘 STOP ACK；此时不能认定云台 CAN1→底盘 CAN2 已通。原始诊断记录为 `logs/usb-diagnostic-before.json`，修复后尚未烧录两板做实物复测。

代码检查并通过软件反例复现了下面的 FIFO 乱序缺陷。它是已确认的软件问题，但还不能认定它是实物无法回包的唯一原因；供电、终端、电缆、错误计数、现有板内固件版本仍待硬件复测。

## 3. 修复内容

原 BSP 按过滤器编号交替选择 FIFO0/FIFO1。导航命令包含 `0x330/0x331/0x332` 三帧，反馈包含 `0x338/0x339/0x33A` 三帧，组包器要求按序到达且在 10 ms 内完成。三帧分到不同 FIFO 后，若两个 FIFO 的中断等待处理，回调顺序可能与总线到达顺序不同，导致组包器丢弃一整组。

修改如下：

1. 两块板 `bsp/can/bsp_can.h` 的注册配置新增 `rx_fifo_policy`，可显式指定 FIFO0/FIFO1；值为 0 时保留 AUTO 行为，兼容其他零初始化端点。
2. 两块板 `bsp/can/bsp_can.c` 配置过滤器时应用该策略。
3. 底盘 `modules/chassis_comm/chassis_comm_port.c` 将三个命令过滤器全部指定 FIFO0。
4. 云台 `application/communication/nav_gateway_port.c` 将三个反馈过滤器全部指定 FIFO0。
5. 测试改为延后交付 FIFO 中的帧，模拟两个中断同时等待；增加旧策略失败、新策略通过的可重复对照回归。

实际源码目录：

- 底盘：`chassis_driver/basic_framework/`。
- 云台：`communication_reference/gimbal_firmware/`。

USB 帧格式、CAN ID、1 Mbps 速率、单位、会话/序号/CRC 与 STOP/TTL 机制保持原协议。电脑测试工具无需因此更改协议。`communication_reference/chassis_firmware/` 是旧参考，不能用它替代本次模块化底盘源码。

保持电机主电源断开，两块板和下载器按实际需要供电，分别烧正确固件。烧录完成后，电脑接云台板自身 USB，云台 CAN1 接底盘 CAN2，H-H、L-L、公共地；不要把下载器串口当应用串口。本项不需要雷达。

```bash
cd /home/wangjiaming/桌面/DiPan_Board
ls -l /dev/serial/by-id/
PORT='/dev/serial/by-id/usb-YueLuEmbedded_RM_Nav_Convert_SP_315F326E3034-if00'
```

`PORT` 必须以当前设备列表为准。先关闭占用同一串口的导航节点和串口工具。零速度测试约 5 秒，全程 ENABLE=0，至少收到 10 帧持续新鲜的底盘 STOP ACK 才 PASS。仅有云台遥测不满足这个条件。完整指令另见 `编译烧录与通信测试指令.txt`。

## 6. 保留的限制和未确认项

- ARM 底盘固件保持 `CHASSIS_COMM_ALLOW_MOTION=0`、`CHASSIS_COMM_AXES_VERIFIED=0`，用于通信测试，默认不驱动轮子；不会为消除 fault 而伪造遥控/电机在线。

- 协议承载期望速度和状态反馈；没有新增障碍物距离、语义标签，也没有替代完整云台/发射/裁判/手动驾驶功能。
